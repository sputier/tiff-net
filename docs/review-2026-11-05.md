# Revue complète d'Eleris.TiffNet — 5 novembre 2026

> **Contexte.** Cette revue porte sur la **première implémentation**, une façade sur un fork de BitMiracle LibTiff.Net
> (ancien dépôt, historique non conservé ; les références `fichier:ligne` pointent vers ce code). Ses conclusions ont conduit à
> réécrire la bibliothèque de zéro, comme Eleris.FitsNet, avec le décodage JPEG inclus, en ciblant net10.0 sur Windows, Linux et
> MAUI. Elle reste la référence des exigences : chaque constat SEC/PERF/DOM/MAINT doit être couvert par la nouvelle
> implémentation. Les outils et fichiers cités sont rapatriés dans [`research/review-2026-11`](../research/review-2026-11/README.md).

Revue de `master` @ `bfe81eb` sur quatre axes : sécurité, performance, métier, maintenabilité. Chaque constat est appuyé par une
lecture de code (`fichier:ligne`) ou une mesure reproduite ; ce qui n'a pas pu être vérifié est signalé. Les fichiers de
reproduction, benchmarks et harnais sont dans le scratchpad de la session (chemins en fin de document).

## 1. Synthèse

| Axe | Verdict | En une phrase |
|---|---|---|

| **Performance** | 🟠 Lecture correcte en mono-thread, **écriture Deflate très lente**, rien n'est parallèle | Lecture Deflate ≈ 160 Mo/s (= tifffile 1 thread), écriture Deflate **11 Mo/s** (u16). Un prototype mesuré atteint 1,3–1,6 Go/s en lecture et 10–13× en écriture. |
| **Métier** | 🟠 Les pixels sont justes, **les fichiers ne survivent pas** | Lecture bit-exacte de fichiers Siril/tifffile/Pillow, mais l'en-tête Astro-TIFF (FITS dans `ImageDescription`), l'ICC, la sémantique des canaux sont perdus ; une miniature en IFD0 est renvoyée silencieusement. |

**Ce que j'ai affirmé à tort dans le README / la doc** (à corriger en priorité, ce sont des promesses publiques) :

- « Un fichier endommagé échoue toujours avec `TiffException` » — faux : `OutOfMemoryException` sort sur un fichier de 124 octets (SEC-07).
- « BigTIFF » en lecture — faux pour le **gros-boutiste** : 0/336 fichiers lisibles (bug amont, MAINT-05).
- « BigTIFF beyond 4 GB » en écriture — faux : l'écrivain n'écrit jamais de BigTIFF.
- « Fuzzé sur 200 000 mutations » — vrai mais non reproductible : le harnais n'est pas dans le dépôt.
- « Rejeté avant d'être alloué » — vrai seulement pour le buffer final de pixels.

## 2. Les décisions structurantes

Les quatre revues convergent sur trois décisions qui conditionnent le reste du backlog.

### D1 — Stratégie vis-à-vis de LibTiff.Net

L'hypothèse du fork (« garder le code amont intact pour fusionner ses correctifs ») ne tient plus : aucun commit amont depuis le
18/12/2024 (vérifié par `git ls-remote` le 05/11/2026), et le seul bug trouvé par l'oracle indépendant doit être corrigé ici.
En contrepartie elle coûte : analyseurs et nullable désactivés sur 41 k lignes, double build (public netstandard2.0 testé /
interne livré non testé par la suite amont), CRLF/BOM mélangés, 22 k lignes inatteignables dans la surface d'attaque.

Trois options :

| Option | Contenu | Pour | Contre |
|---|---|---|---|
| **A. Durcir le fork tel quel** | Patches `Eleris:` ciblés (SEC-01…06), garder la structure | Rapide | Ne règle ni la perf, ni la maintenabilité ; on patche un code qu'on ne possède pas |
| **B. Absorber et élaguer** | Déplacer dans `src/`, normaliser LF, supprimer le build public, outils, samples, codecs inutiles (~22 k lignes), remplacer zlib par `System.IO.Compression` | Réduit la surface d'un tiers, débloque analyseurs et perf | Reste 15–20 k lignes de code porté C de 2006 dont on hérite les classes de bugs |
| **C. Implémentation possédée** | Lecteur/écrivain propre au périmètre (IFD classique + BigTIFF, grey/RGB, 8–64 bits, None/LZW/Deflate/PackBits, prédicteurs 2/3, strips/tuiles) ≈ 3–4 k lignes, LibTiff gardé seulement comme oracle de test ou pour le JPEG | Cohérent avec FitsNet (code possédé), parallélisme natif, bornes de sécurité conçues dès le départ, perf maîtrisée | Effort L ; risque de compatibilité à couvrir par un corpus d'interop tifffile |

**Recommandation : A immédiatement (quelques patches S, parce que la lib peut déjà être utilisée), puis C.** Arguments :
le prototype de performance (PERF-03) n'utilise déjà plus LibTiff que pour lire le répertoire, et c'est précisément là que se
trouvent les dénis de service (SEC-01/02/03). Le périmètre utile est petit et bien spécifié (TIFF 6.0 + BigTIFF + TN3), et le
corpus tifffile (2 208 fichiers, déjà généré) fournit l'oracle pour garantir la compatibilité. B est une étape intermédiaire
raisonnable si C paraît trop gros, mais on investirait dans un code destiné à disparaître.

### D2 — Modèle d'API 1.0 (changements cassants à trancher avant 1.0)

1. **Fichier vs image** : introduire `TiffFile` (ouverture paresseuse, pages, `Primary` = première image pleine résolution) ;
   `TiffImage.Read` reste un raccourci « première image pleine résolution », pas « IFD0 ».
2. **Métadonnées** : `TiffMetadata` immuable (record + `with`) pour garder la garantie « immuable, partageable entre threads » ;
   conservées par défaut lors d'une lecture → écriture.
3. **Modèle couleur explicite** (`Grey` / `Rgb`) au lieu de « ≥ 3 canaux ⇒ RGB » ; canaux supplémentaires typés
   (`Data`, `AssociatedAlpha`, `UnassociatedAlpha`).
4. **Accès aux pixels aligné sur FitsNet** : `ReadPixels<T>(conversion)` → `T[]` avec conversion (`Exact`/`Cast`/`Normalize`),
   `RawPixels<T>()` → `ReadOnlyMemory<T>` sans copie, `ReadRegion`, `ReadChannel`. Retirer `GetPixels`.
5. **Stockage typé `T[]`** au lieu de `byte[]` : lève le plafond de 2 Go à 2³¹ éléments (8 Go de float) et donne `Memory<T>`.
6. **Ordre des arguments de `Create`** (pixels en premier comme FitsNet, ou non — mais décidé une fois) ; une variante
   « prend possession » sans copie.
7. **Valeurs d'enums figées**, `Float16` réservé.
8. **Options** : `TiffReadOptions` (limites, page, annulation) ajouté dès maintenant en paramètre optionnel ; records.
9. **Taxonomie d'exceptions** : distinguer « non supporté » et « endommagé » (FitsNet utilise `NotSupportedException`).
10. **Contrat de normalisation** : jamais implicite ; non-signé ÷ max du type → [0,1], signé → [-1,1], float inchangé.

### D3 — Cibles .NET

net8.0 sort du support le **10/11/2026**. Décider : garder net8 une version de plus ou passer net10 seul (à appliquer aussi à
FitsNet). À noter : la piste `System.IO.Compression` est nettement plus rapide sur net10 (zlib-ng) que sur net8.
